Design exploration v2 · 2026-05-07

Group review — three mockups

A second pass after rejecting the GitHub-PR-aesthetic. GitHub presence is now a thin activity strip (branches, commits, PRs as events with links). The file surface explores three different group review metaphors — reading room, whiteboard, round table.

What changed: GH is references-only, no embedded PR UI What's new: three different "group review" file surfaces Companion to: 06-github-and-files-integrated.html

00The new direction

GitHub is a sidekick now, not the frame. The file surface is where group review actually happens.

The thin gh-strip at the top of every mockup tracks GitHub events that happened during this session — a branch was created, a commit was pushed, a PR was opened — with links offsite. No PR shell, no Files-changed tab, no reviewer avatar rails. If a watcher wants to look at the actual PR, they click through to GitHub.

The file surface is doing the real work, and each of the three mockups below picks a different metaphor for what "group review" looks like. They share data plumbing — touched files, per-line annotations from watchers, presence indicators — but the framing is different in each one. Pick the framing first; the plumbing comes for free.

Quiet, manuscript-feeling. The file is the primary text. Watchers leave margin notes with leader lines; their reading position shows as a soft underline. Like a marked-up paper everyone in the room is reading at the same time.

A single touched file held open like a manuscript. Lines changed this session glow softly. Watchers' selections show as colored underlines (kavi sage, mira lilac). Presence dashes mark where each watcher is reading right now. Margin holds threaded annotations with dashed leader lines back to anchored ranges.

Strengths
  • Calm, focus-friendly — works for one file at a time
  • Comment-anchoring is obvious because the metaphor demands it
  • Presence is informative without being noisy
  • Different watchers in different colors actually scales to ~6
Caveats
  • Single-file focus means the file picker tabs need to feel light or this becomes navigationally annoying
  • Live edits to the visible file mid-read can yank the reader's attention — needs a "pause auto-update" toggle
  • Collaborative selection sync is the most expensive thing to build right (10× harder than the UI)

Strengths
  • Multi-voice — you feel everyone in the room at once
  • Reactions are quick and low-friction (often what watchers actually want)
  • Visual hierarchy makes the “hot” lines obvious
  • Works for the “everyone reacting in real time” pairing-session shape
Caveats
  • Density gets out of hand on big diffs — needs note-collapse and a “hide reactions” toggle
  • Live cursors over a public tunnel will be laggy (200ms+) — design for the lag, not against it
  • Sticky notes are charming but not searchable — pair with a flat threaded view in a sidebar

A single chronological feed. Host prompts, Claude responses, file changes (as inline mini-diffs that expand on demand), watcher comments, and GitHub events (branch, commit, PR — dashed cards) all interleave. Each item has a seen-by ribbon and reaction chips. Comments thread directly underneath the thing they're anchored to.

Strengths
  • One scroll surface to follow — easy to "catch up" if you arrive mid-session
  • File changes get the same weight as turns, so review lives in the flow rather than in a separate tab
  • Seen-by ribbons make it obvious what's actually been read by whom
  • GitHub events are quiet (dashed, mono) and don't compete with the human voices
Caveats
  • Long sessions get long fast — needs collapsing, jump-to-turn, and "show only file changes" filters
  • Less spatial than the whiteboard — harder to see "everyone is talking about line 148"
  • Inline mini-diffs help but for big changes you still want a full viewer somewhere

04What to pick

The three aren't a ladder — they're three different bets on what "group review" feels like. Reading room is contemplative and best for one file at a time. Whiteboard is energetic and best for live pairing on a single change. Round table is narrative and best for catching up or reviewing async.

You can also mix. The whiteboard's reaction-on-line affordance and the reading room's margin notes share the same data shape (per-line annotation with author + body + reaction count). The round table's seen-by ribbon and the reading room's presence indicators share the same data shape (per-watcher last-seen turn or line). Picking a primary metaphor doesn't lock out features from the others.

The thin GitHub strip is identical in all three on purpose — it's a chronological band of branch_created, commit_pushed, pr_opened events with offsite links. It can grow inline event types later (review_left, workflow_failed) without changing the surface beneath it.
