Connecting Better Together to GitHub & surfacing shared files

Three paired designs — minimum-viable to ambitious — for wiring full GitHub context into a room and giving lobby viewers files they can actually look at, not just events that say a file changed.

Scope: two related features explored together Constraint: host-machine-only, no central service Aesthetic anchor: design-pocs/05-pr-review.html Companion to: PRD.md
The three designs
  1. Repo sidecar + auto-touched filestier 1 · ~3 days
  2. PR-anchored room + pinned files panetier 2 · ~1–2 weeks
  3. Workflow hub + time-travel file browsertier 3 · ~1 month

00Why these two features pair naturally

A room without GitHub context floats; a room without file content is opaque. They’re the same problem — making the host’s session legible — from two sides.

Today the lobby renders prompts, responses, and tool-call events. A watcher learns that server.js was edited at turn t14, but cannot see what changed. They learn the host is working on something, but not what repo, what branch, what PR, whether CI is green.

Both gaps point at the same thing: the lobby needs to be a review surface, not a livestream caption. The three designs below walk a single ladder from "passive metadata" to "the room is a workflow hub and a time-travel inspector." Each tier picks a matching pair from the GitHub side and the files side, so commitments stay coherent — you don't end up with a workflow-hub GitHub integration sitting on top of an opaque transcript.

What "GitHub context" means here

  • Repo + branch + working-tree status
  • PR for current branch (number, title, state, draft)
  • PR diff (files changed + hunks)
  • CI / check-runs status
  • Linked issues for the PR or branch
  • Recent commits, reviewers, labels

What "shared files" means here

  • Touched files (auto-discovered from tool calls)
  • Diff snapshots (per-edit before/after, plus rolling diff vs git HEAD)
  • Pinned files (host-curated, always live)
  • Repo browser (full read of CWD, allowlisted)
  • Time-travel snapshots anchored to specific turns

Mechanism, in one sentence: the host’s server gets a small github.js adapter (wraps gh CLI, no new deps) and the existing transcript-tailer.js grows a sibling step that captures file contents on every Edit/Write tool result. Both feed the same in-memory store and the same SSE bus, plus targeted on-demand HTTP endpoints for fat payloads. No central service. No npm install. The host’s gh auth token is the single credential surface.

01Repo sidecar + auto-touched files

The cheapest version of both ideas, glued onto today’s lobby with no schema changes and no new host commands. Auto-detected, read-only, ~3 days end to end.

Complexity: low ~3 days No new commands Read-only Zero new deps

GitHub side — passive sidecar

  • On host start: git remote get-url origin + gh pr view --json (auto-link)
  • Poll: PR header every 30s, CI checks every 15s
  • Render: a repo / branch / PR pill / CI lights strip just under the room URL
  • Click PR → opens GitHub in a new tab. Read-only, no mutation.

Files side — auto-touched strip

  • Extend transcript-tailer.js to capture path + contents on every Edit/Write tool result
  • In-memory ring buffer, LRU-evicted at 50 distinct files
  • Render: horizontal pill strip; click → modal diff view (vs HEAD)
  • Fully automatic — zero host action required

A new GitHub strip sits where the room URL used to be. Below the transcript (not shown), an auto-populated dark file strip lists every file Claude touched; clicking a pill opens the diff modal under it.

Earns its keep
  • Watcher orientation in the first 2 seconds — "this is PR #142, 2 of 3 checks green, here are the touched files"
  • Reuses what transcript-tailer.js already extracts (tool_input.file_path)
  • No host commands, no MCP, no schema changes
  • SSE-friendly: file metadata fits in the stream; bodies are on-demand HTTP
What it doesn’t do
  • No way to view a file Claude hasn’t touched yet
  • No comment-anchoring to file lines (still turn-level)
  • No CI history, no review workflow, no issue context beyond the PR title
  • Polling-fallback viewers see file metadata 2.5s late — usually fine
Why ship this first. It’s the smallest change that makes the lobby legibly more useful for review. Everything in tier 2 and tier 3 is a strict superset that reuses the same github.js adapter and the same fileStore.

02PR-anchored room + pinned files pane

The room is a PR. Tabs replicate GitHub’s review surface; comments can mirror to PR review-comments; the host curates a pinned-files side rail with always-live contents.

Complexity: medium ~1–2 weeks New host commands Optional bidirectional comments MCP tools for plugin watchers

GitHub side — PR-anchored room

  • Full PR header (state-pill, title, branch → into, draft, reviewers)
  • Tabs: Conversation / Commits / Files changed / Checks / Issues
  • CI banner with per-check expandable details, live spinner
  • Lobby comments can opt-in mirror to PR review-comments (anchored by tool-call file:line)
  • Host commands: /better-together:gh-pr, gh-mirror on|off, gh-checks
  • MCP tools: gh_pr_files, gh_pr_diff, gh_pr_checks, gh_post_pr_comment (host-gated)

Files side — pinned pane

  • Host explicitly pins via /better-together:share <path>
  • Each pinned file becomes a tab in a left-side rail; fs.watch + 200ms debounce keeps it live
  • Live edits show a "live" pulse; lines edited this session glow with a turn-id gutter
  • Both Claude edits and direct editor edits land — the rail is "what should I keep an eye on"
  • Per-pin allowlist + redaction pass; share .env is rejected with a host-visible reason
  • Audit log to ${CLAUDE_PLUGIN_DATA}/file-access.log

PR shell up top (header, state pill, tabs, CI banner) wraps a pinned-files surface. The "Files" tab is selected; the pinned rail on the left is the host’s curated working set. Lines touched in this session glow orange with the turn id in the gutter.

Earns its keep
  • Reviewers recognize the surface instantly — tabs match GitHub
  • Pinned files mean the host curates exactly what watchers should focus on
  • Optional comment-mirroring lets a room produce a real PR review without context-switching
  • MCP tools give plugin-watcher Claudes repo-aware context without giving them a token
Watch out for
  • Diff payloads bloat snapshot.json — serve diffs at /github/diff lazily
  • macOS fs.watch is flaky on swap-rename saves; need fs.watchFile fallback
  • PR-comment mirroring needs idempotency keys to survive reconnects
  • Private repos — auto-link should be opt-in, not default

03Workflow hub + time-travel file browser

The room becomes a two-way GitHub workspace and a recording. Webhooks land in the timeline, watchers can act on the PR from inside the lobby, and every transcript turn snapshots the file tree so picking turn t27 rewinds the file pane to that moment.

Complexity: high ~1 month Bidirectional Audit log non-optional Disk-backed snapshot store Per-action ACL

GitHub side — bidirectional hub

  • Webhooks (push, PR review, issue_comment, workflow_run) land in the room timeline
  • Color-coded card kinds: host turns / webhooks / watcher actions
  • Watchers can file issues, request review, label, approve PRs — gated by host-approval-in-terminal
  • Live workflow-log streaming (gh run watch) into the lobby
  • Full MCP tool surface: gh_create_issue, gh_request_review, gh_approve_pr, gh_label_set, gh_workflow_rerun
  • Webhook reachability solved by gh webhook forward subprocess, not by registering the ephemeral tunnel URL

Files side — time-travel browser

  • Full repo tree (filtered by allowlist + .gitignore) seeded from git ls-files
  • Every transcript turn captures a snapshot of every file it touched, content-addressed by sha
  • Scrubber rewinds the file pane to "as-of turn t27"
  • Disk-backed store (${CLAUDE_PLUGIN_DATA}/snapshots/<sha>.txt) keeps RAM bounded
  • Per-room byte cap (max_session_bytes, default 50 MB), audit log per file access
  • Comment anchoring graduates from turn-level to file:line at a specific turn

Lighter, document-y aesthetic for the file inspector to set it apart from the timeline. Tree on the left (touched-count dots per file), file shown "as of t27" not at HEAD, right rail lists every turn that touched this file plus a scrubber that rewinds the whole pane.

Earns its keep
  • Comments graduate from turn-level to file:line@turn — the unblocker for serious review
  • Scrubbing is the most-asked feature in any "watch a recording" tool, including the PRD’s own §Problem section
  • Watchers stop having to context-switch to GitHub to act on the work they’re watching
  • Auto-published "host edited X" PR comments give async observers a natural breadcrumb
Real work to make this safe
  • "You have the URL" is no longer enough authority — mutations need per-action ACL
  • Webhook reachability under quick-tunnel is the single biggest unknown; gh webhook forward is the workaround
  • Disk-backed snapshot store + byte cap or RAM blows up on long sessions
  • Audit log non-optional — surfaced in /better-together:files-log
  • Plugin watchers’ local Claudes could mass-fetch every file via watch-context; default to metadata-only-to-plugin-watchers

05Risks & open questions

Things that are real concerns regardless of tier — worth resolving before commitment, not after.

  • Cloudflare buffers SSE. The README already documents the polling fallback for transcripts. File-snapshot SSE events must be metadata-only; bodies are one-shot HTTP at /files/get so they bypass the buffer.
  • Auto-link false positives. A repo with git remote = github.com:org/repo but no PR yet means gh pr view errors. Distinguish "no PR for this branch" (silent) from "auth failed" (surfaced).
  • Private-repo leak via the public tunnel URL. Default the GitHub integration to "off for private repos" with explicit opt-in (/better-together:gh-bind confirmation).
  • Webhook reachability under quick-tunnel. Ephemeral URLs make repo-level webhook installs untenable. Use gh webhook forward subprocess instead — per-host, no admin scope on the repo, dies cleanly with the room.
  • Path safety beyond the obvious. CWD allowlist, symlink resolution via fs.realpathSync.native, default-deny on .env*, .ssh, .aws, *.pem, id_rsa*, plus .gitignore matching. 50-line minimal-ignore matcher to stay zero-deps.
  • Plugin-watcher analyst Claudes are scarier than browser watchers. Their local Claudes can ingest file contents and exfiltrate via tool calls. Default files_to_plugin_watchers = "metadata"; bodies require explicit per-room flip.
  • PR-comment mirroring needs idempotency. Reconnects mustn’t double-post. Use a stable (room_id, turn_id, comment_id) key as the GH comment’s identifier.
  • Snapshot eviction policy. LRU is right for tier 1 but breaks tier 3’s "every turn forever" semantics. Disk-backed store with sha-content addressing dedupes most of the cost; a per-room max_session_bytes cap is the floor.
  • Race on file capture. If the host’s editor saves over Claude’s edit between tool_use and tool_result, we’d capture the editor’s content tagged with Claude’s turn id. Mitigation: when an Edit tool has tool_input.new_string, prefer that over disk read.
  • "You have the URL" stops being enough authority at tier 3. Mutating GH state on the host’s behalf needs at minimum per-action approval in the host’s terminal — same shape as the existing comment notification, but with an explicit allow/deny prompt.
